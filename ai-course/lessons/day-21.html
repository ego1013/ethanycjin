12 min

Step 1：任务拆解 — 你的工作到底在做什么？

场景还原

假设每月月初，你需要完成一件事：全国代理商的月度绩效分析。

这件事今天你大概是怎么做的？

① 数据拉取（~1天）：从系统导出各代理商上月的出货数据、回款数据、客户投诉数据、合同执行数据
② 异常标记（~0.5天）：找出偏离目标的代理商——谁没达标？谁突然下滑？谁超额完成？
③ 原因分析（~1.5天）：对异常代理商逐个分析原因——是季节性波动？市场环境变化？还是经营问题？
④ 对策建议（~1天）：给每个异常代理商拟定下一步行动——沟通计划、支持方案、或预警处理
⑤ 报告撰写（~1天）：把以上内容整合成绩效分析报告，呈送管理层

总计：~5 个工作日

现在，用 Day 20 的四步判断法，对每个步骤做可验证性分级：

步骤 验收标准 验证成本 反馈回路 可验证性
① 数据拉取 数据完整、无缺失、格式正确 秒级自动校验（行数/列数/空值检测） 立即可见 ✅ 高
② 异常标记 符合预设规则的异常全部标出 规则匹配，自动核验 立即可见 ✅ 高
③ 原因分析 因素归纳合理、数据支撑到位 数据相关性可验证，归因逻辑需人判断 需人审核 🟡 中
④ 对策建议 可执行、有针对性、考虑现实约束 "可执行性"需了解团队能力和客户关系 需人判断 🔴 低
⑤ 报告撰写 结构清晰、数据准确、观点鲜明 数据部分可自动验证，观点部分需人把关 部分自动/部分人审 🟡 中
💡 关键发现

5 个步骤，可验证性从 ✅ 到 🔴 逐级递减——越往下越需要人的判断力。

这意味着：
• 步骤 ①② 可以让 AI 全自动完成（高可验证 → 出错可自动发现）
• 步骤 ③⑤ 可以让 AI 出初稿 + 人审核（中可验证 → 数据部分信任，判断部分人把关）
• 步骤 ④ 只能让 AI 提供参考选项，人做最终决策（低可验证 → 依赖关系洞察和业务直觉）

先做了这一步分级，整个工作流的架构就自然浮现了。

Step 2：架构设计 — 组装你的 Agent 系统

架构选择：为什么选 Orchestrator 模式？

回顾 Day 19 讲的四种 Multi-Agent 架构，这个场景最适合哪种？

• 流水线？ 步骤之间有严格顺序依赖（③ 需要 ②的结果），部分适合。但步骤之间信息粒度差异大——① 是结构化数据，④ 是自然语言建议——纯流水线容易在"格式转换"中丢失信息。

• Orchestrator + Workers？ ✅ 最佳选择。原因——

🏗️ 为什么选 Orchestrator？

① 有一个"全局视角"需求——Orchestrator 能看到所有代理商数据的全貌，协调不同 Worker 的优先级
② 步骤之间有"条件分支"——不是所有代理商都需要走到步骤 ④，只有异常的才需要
③ 人介入点明确——Orchestrator 在步骤 ③→④ 的交接处暂停，等待人审核后再继续
④ 错误隔离——某个 Worker 出错不影响整体流程，Orchestrator 可以重试或绕过

逐个 Agent 的详细设计

接下来，对每个 Agent 做具体设计。这里用到 Day 15-18 的所有武器：

🔧 Worker A：数据拉取 Agent
职责：从业务系统获取结构化数据，完成清洗和标准化
设计维度 具体方案 对应课程
工具配置 数据库查询 API（只读权限 🟢）、数据格式校验脚本 Day 18 工具调用
记忆 无需记忆——每次执行独立，数据实时拉取 Day 18 记忆方案
验证方式 自动校验：行数 ≥ 预期、无空值关键列、时间范围正确 Day 20 验证成本
失败策略 校验失败 → 重试 1 次 → 报错给 Orchestrator → 人工排查 Day 17 可靠性

Prompt 设计要点（CRISP）：
Context：你是渠道绩效数据系统的数据提取助手
Role：精确执行数据查询，不做任何推断
Input：时间范围、代理商范围、指标列表
Specification：输出 JSON 格式，必须包含字段 [id, name, region, metrics...]
Persona Check：如果任何字段为空，标记而非填充默认值

🔍 Worker B：异常检测 Agent
职责：基于预设规则标记绩效异常的代理商
设计维度 具体方案 对应课程
工具配置 统计计算函数（均值/标准差/环比）、规则引擎 Day 18
记忆 上下文注入：当月规则集 + 上月基线数据（~5K字，无需向量库） Day 18 记忆方案
CoT 策略 逐代理商逐规则判断（Step-by-step），避免遗漏 Day 16 CoT
验证方式 双重校验：规则引擎独立跑一遍 vs Agent 标记结果，不一致则报警 Day 20 验证独立性
失败策略 不一致数 > 5% → 暂停 → 人工抽检 Day 17

异常规则示例：
• 出货量环比下降 > 20%
• 回款周期超过合同约定 > 15 天
• 客户投诉量环比增加 > 50%
• 连续 2 个月未达标
（规则由人定义和更新，AI 负责执行——标准制定是人的事，规则执行是 AI 的事）

🧠 Worker C：归因分析 Agent
职责：对异常代理商进行原因初步排查，生成分析假设
设计维度 具体方案 对应课程
工具配置 数据查询（历史趋势）、行业数据 API、市场信息检索（RAG） Day 18
记忆 结构化摘要：该代理商近 6 个月变化轨迹 + 上次异常的归因结论（~300字/代理商） Day 18 三层混合
CoT 策略 强制 CoT 五步推理：数据确认 → 趋势识别 → 外部因素排除 → 内因假设 → 信心度评分 Day 16 Few-shot CoT
验证方式 数据引用可核实（✅）+ 归因逻辑人审核（🟡）+ 信心度标注提示审核优先级 Day 20 部分可验证
失败策略 信心度 < 60% → 标记"需人工深入分析" → Orchestrator 跳过自动流程 Day 17 HitL
🎯 CoT Prompt 模板（Worker C 核心）

你是渠道绩效分析师。请对以下异常代理商进行原因分析。

## 分析步骤（必须逐步执行）
1. 确认异常事实：哪个指标偏离了什么标准？偏离幅度？
2. 趋势分析：是突变还是渐变？近 3-6 个月的趋势如何？
3. 排除外因：区域整体是否都在下滑？是否有季节性因素？市场环境变化？
4. 归因假设：列出 2-3 个可能的内因，每个附上支撑数据点
5. 信心度：给出 0-100 的信心评分，说明不确定的部分是什么

## 输出格式
{"agent_id": "...", "anomaly": "...", "analysis_steps": [...], "hypotheses": [...], "confidence": 75, "uncertain_factors": ["..."]}

## 规则
- 不确定的因素必须明确标出，禁止编造数据
- 信心度 < 60 时，必须标记为"需人工深入分析"
- 所有数据引用必须注明来源（系统数据/行业报告/历史记录）

📝 Worker D：报告生成 Agent
职责：将分析结果整合为结构化绩效报告
设计维度 具体方案 对应课程
工具配置 模板渲染引擎、图表生成（趋势图/对比图）、文档输出（PDF/PPT） Day 18
记忆 上下文注入：报告模板 + 上月报告结构（确保格式一致性） Day 18
Prompt 策略 Negative Prompting 防止观点注入："只陈述数据和分析结果，不做战略建议" Day 15 杠杆

失败策略 数据不一致 → 重新生成；人审不通过 → 标记修改点 → Agent 修订 Day 17

职责：协调四个 Worker 的执行顺序、处理异常、管理 Human-in-the-Loop 节点
设计维度 具体方案 对应课程
执行策略 A → B → C（仅异常） → 暂停等待人审 → D Day 19 协调
记忆 结构化摘要：本次执行状态、各 Worker 结果摘要、人的审核批注 Day 18

Human-in-the-Loop 设计：人在哪里介入？

Day 17 讲过——Agent 系统中人的位置至关重要。这个系统有两个人工审核节点：

节点 位置 审核内容 预计用时
审核点 1 Worker C 完成后 归因分析是否合理？有没有遗漏的重要因素？信心度低的需要人补充分析 ~30 分钟
审核点 2 Worker D 完成后 报告的观点和结论是否准确？数据呈现是否清晰？行动建议是否可行？ ~20 分钟
✅ 时间效率对比

原来（纯人工）：5 个工作日 ≈ 40 小时
现在（AI + 人审核）：
• Worker A + B 全自动：~5 分钟（原来 1.5 天）
• Worker C 自动分析：~15 分钟（原来 1.5 天）
• 人审核归因 + 补充对策：~1 小时（原来 1 天，但现在有 AI 初稿做基础）
• Worker D 生成报告：~10 分钟（原来 1 天）
• 人终审报告：~30 分钟

总计：~2 小时（从 40 小时压缩到 2 小时，效率提升 ~20x）

更重要的是——人的时间从"机械性数据处理"转移到了"判断和决策"。2 小时里你做的全是高价值的思考工作，而不是复制粘贴和格式调整。

Step 3：质量保障 — 让系统可靠运行

三层防护体系

Day 17 告诉我们 Agent 的可靠性公式是 0.95ⁿ——每多一步出错概率就累积。5 步流程如果不加防护，整体可靠性 ≈ 0.95⁵ ≈ 77%。这远远不够。

解决方案：在每一步之间加验证门，把错误切断在传播之前。

每个 Worker 完成后自动检查

• Worker A → 数据完整性检查：行数/列数/空值率/时间范围
• Worker B → 规则一致性检查：Agent 标记结果 vs 规则引擎独立计算
• Worker C → 信心度阈值检查：低于 60% 的分析自动标记待人审
• Worker D → 数据一致性检查：报告中的数字 vs 源数据交叉验证

✅ 成本：近乎为零（代码自动执行） · 覆盖：所有可验证维度

不可验证环节人工把关

• 归因逻辑审核：人检查 Worker C 的推理链条是否合理
• 对策决策：人基于 AI 提供的分析做最终行动方案（这一步完全由人主导）
• 报告终审：人确认观点表述和结论准确性

🟡 成本：~1.5 小时 · 覆盖：所有不可验证维度

事后可追溯

• 全程日志：每个 Agent 的每次工具调用和推理过程全部记录
• 月度 Review：对比 AI 分析与实际结果（下个月回头看，上个月的归因对不对？）
• 持续优化：根据 Review 结果调整规则阈值和 Prompt——形成"AI 也在学习"的闭环

🔵 成本：月度 30 分钟 · 覆盖：长期准确率持续提升

💡 核心设计哲学

不追求"完美 Agent"——追求"错了能发现、发现了能修复、修复了能记住"的系统。

这就是为什么 Verifiable Problem（Day 20）是整个设计的起点——只有先确认"哪些环节的错误可以被发现"，才能设计出合理的"何时信任 AI、何时请人审核"的边界。

风险预判：这个系统可能在哪里出问题？

风险 发生场景 应对
数据源变更 业务系统 API 接口升级，字段名改变 Worker A 的校验会立即报错 → Orchestrator 暂停 → 通知维护
规则过时 业务调整了异常判断标准但没更新规则集 月度 Review 发现"标记为异常但实际正常"的比例升高 → 触发规则更新
归因幻觉 Worker C 给出"看起来合理但实际上错误"的归因 信心度评分 + 人审核双重保障；月度回溯验证
审核疲劳 人对 AI 输出逐渐放松审核，变成"全部通过" 随机埋入"故意错误"做审核有效性测试（来自 Day 4 Reward Hacking 防御思路）

🎓 第二模块核心认知

你不需要成为工程师来搭建 AI 系统。

你需要的核心能力是：
① 任务拆解（哪些可验证、哪些不可验证）
② 架构设计（谁做什么、谁和谁协作、人在哪里介入）
③ 质量定义（什么算做对了、做错了怎么发现、怎么改进）

这三件事——和你管理一个团队时做的事完全一样。

管理 AI 的能力，就是管理的能力。AI 时代最值钱的人，不是会写代码的人，而是会定义"什么是好的产出"的人。

✅ Checkpoint · Day 21（模块收官）

场景：基于今天设计的系统，一位同事质疑你——"搞这么复杂干嘛？直接让 ChatGPT 看一遍数据出个分析报告不就行了？一个 Prompt 搞定，为什么要拆成 5 个 Agent？"

你怎么回应？

A 他说的也有道理——如果只有 10 个代理商，一个 Prompt 确实够用。现在之所以拆开，是因为代理商数量多（50+），单次 Context Window 装不下所有数据和分析。拆成多个 Agent 本质上是为了解决"信息量超过单次上下文容量"的工程问题。
B 拆开不是为了复杂，是为了可靠。一个 Prompt 搞定意味着——出错时你不知道错在哪一步、哪个数据有问题、哪个推理不对。拆开之后每一步都有验证门，错误可以被精确定位和快速修复。"简单"和"可靠"是两回事。
C 关键不在"几个 Agent"——关键在"哪些环节你敢全自动、哪些环节必须人审核"。一个 Prompt 搞定的方案里，所有步骤都混在一起，你无法在"归因分析"环节单独加人工审核。拆开是为了在不同可验证性等级的环节设不同的信任策略。
D 先问他一个问题：如果 ChatGPT 给出的分析报告里有一个数据错误，你怎么发现？如果归因分析有逻辑漏洞，你怎么定位到具体是哪个推理环节出了问题？如果回答不上来——那就是为什么要拆开。拆的本质不是"让事情变复杂"，是"让错误变得可发现"。

⚡ 追问：如果这个系统每月执行一次，你预计运行多久后需要做第一次"规则更新"或"Prompt 调优"？为什么？

📌 知识卡片

1 AI 工作流设计三步法：拆解 → 架构 → 质量
Step 1 用可验证性分级拆任务（Day 20）；Step 2 选 Multi-Agent 架构并设计每个 Agent（Day 15-19）；Step 3 在每个环节设验证门和 HitL 节点。三步走完就是一个可落地的方案。
2 Orchestrator + Workers：渠道管理最佳架构
有全局调度需求 + 步骤间有条件分支 + 人介入点明确 → Orchestrator 模式最优。避免过度拆分（协调成本）或过度合并（错误不可定位）。
3 Human-in-the-Loop 位置 = 可验证性边界
人审核节点应该设在"可验证→不可验证"的分界处。高可验证步骤之间不需要人（自动验证门够了），只在进入判断性决策前加人工审核。
4 效率提升 = 从 40 小时 → 2 小时（20x）
关键不是"AI 代替了人的全部工作"——而是"AI 做了 80% 的机械性工作，人只做 20% 的判断性工作，且这 20% 有 AI 初稿做基础"。人的角色从"执行者"变为"审核者和决策者"。
5 管理 AI 的能力 = 管理人的能力
定义产出标准、分配任务、设审核节点、处理异常——你管理 Agent 用的能力和管理团队一模一样。AI 时代最值钱的不是写代码的人，而是能定义"什么是好的产出"的人。

🔗 前序知识连接

Day 15 CRISP 框架在每个 Worker 的 Prompt 设计中都被使用。特别是 Worker C 的归因分析 Prompt——Context 定义角色、Rules 约束行为、Input 提供数据、Specification 定义输出格式、Persona Check 防止幻觉。
Day 16 CoT 是 Worker C 的核心武器——强制五步推理链（数据确认→趋势识别→排除外因→内因假设→信心度），让归因过程透明可审核。如果不用 CoT，AI 直接给结论，人无法判断推理是否合理。
Day 17 Agent 的可靠性公式（0.95ⁿ）是设计验证门的直接依据——每步之间加检查，把整体可靠性从 77%（无防护）提升到 95%+（有验证门）。Human-in-the-Loop 节点对应 Day 17 讲的"该给 Agent 多大自主权"。
Day 18 每个 Worker 的工具集和记忆方案都来自 Day 18 的设计原则——工具权限分级（Worker A 只有只读权限）、记忆方案选择（Worker C 用结构化摘要而非全量向量检索，因为数据量 < 30K 字）。
Day 19 选择 Orchestrator 而非流水线或 Swarm，是基于 Day 19 的架构选择原则——有条件分支 + 人介入点 + 全局视角需求 → Orchestrator 最优。通讯方式采用共享记忆 + 事件驱动。
Day 20 整个设计的起点——先用可验证性四步判断法对 5 个步骤分级，才能决定"哪些全自动、哪些人审核、哪些人主导"。Verifiable Problem 是 Agent 工作流设计的第一原则。
