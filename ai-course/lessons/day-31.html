AI产品设计原则(3)：Agent产品设计

当 AI 不只是"分析"还要"动手做事"——可靠性管理从加分项变成了生死线
📅 2026-05-20 Wed ⏱️ 约 40 分钟 🟡 中半衰期
🔥 开场问题

Day 29 讲长文本——AI 帮你"看"200 页合同，给你分析结论。出了错？你多看一眼就发现了。
Day 30 讲多模态——AI 帮你"看"门店照片，标注违规区域。出了错？你对照照片就发现了。

但今天的场景不一样：AI 替你发了一封邮件给代理商，通知他下季度返利降为 0。

邮件发出去了。代理商电话打进来了。你才发现——AI 把"低于目标 5%"错误理解为"低于目标 50%"，一个小数点导致了一封不该发的通知。

这就是 Agent 产品设计的根本不同：错误不再是"可被发现的分析偏差"，而是"已经执行的不可逆动作"。
产品设计的核心命题，从"信息管理"变成了"行动可靠性管理"。

10 min

Why — 为什么 Agent 产品设计值得单独一课

1. "分析型"vs"行动型"——产品设计的根本分野

Day 29 和 Day 30 本质上都是"分析型"AI 产品设计——用户给输入，AI 给分析，用户决定怎么做。AI 的输出是"建议"，决策权在人手上。

而 Agent 产品的本质不同：

核心区别

分析型产品：AI输出 = 信息/建议 → 错误后果 = 人多花 10 分钟检查
Agent产品：AI输出 = 实际动作（发邮件/改数据/调系统）→ 错误后果 = 不可逆的业务损害

这意味着 Agent 产品的设计核心不是"让 AI 更聪明"，而是"让 AI 犯错时伤害最小化"。

2. Day 17-21 讲了"机制"，今天讲"产品化"

回忆一下第二模块的知识储备：

  • Day 17：Agent 的定义、Perceive-Think-Act 循环、三个边界（可靠性/幻觉放大/权限悖论）
  • Day 18：Function Calling、工具调用失败模式、记忆三方案
  • Day 19：Multi-Agent 架构、通讯损耗、协调成本
  • Day 20：可验证性分级、什么任务适合交给 AI
  • Day 21：完整设计了渠道绩效 Agent 工作流

那些都是底层机制——"Agent 是什么/能做什么/有什么风险"。

今天讲的是产品设计层——"同样的 Agent 能力，怎么包装成用户敢用、愿意用、用了不出事的产品"。

类比：渠道管理的"三级授权体系"

你不会把所有权限一次性给新渠道经理——你设计了分级授权+审批流+异常熔断。
低风险操作（查数据）不用审批；中风险操作（调价格）需要主管确认；高风险操作（终止合作）需要总监签字。
Agent 产品设计本质上就是给 AI 设计一套"组织管理制度"——什么能自动做、什么要报批、什么绝对不能做。

3. 为什么现在市面上大部分 Agent 产品都不好

2025-2026 的 Agent 产品爆发期，绝大多数产品犯了同一个错误：

  • Demo 思维：展示"AI 能做到"就结束了，没有设计"AI 做错了怎么办"
  • 把"能力"当"产品"：模型可以调 API 了 → 就直接让它调 → 没有权限分级、没有预确认、没有回滚
  • 忽视用户信任建立：第一次使用就让 AI 执行高风险操作 → 用户出一次事就永远不信了

结果就是我们看到的行业现状：Agent 的技术 demo 很惊艳，但用户留存率极低——因为产品设计没有解决"信任"问题。

What — Agent 产品设计的五个核心维度

核心框架：Agent 产品的"信任飞轮"

Agent 产品设计的终极目标不是"让 AI 做更多事"，而是建立用户对 AI 行动的信任，让用户逐渐愿意把更多决策权交给 AI。这是一个飞轮：

┌─────────────────────────────────────────────────────────┐ │ Agent 产品设计 · 信任飞轮 │ ├─────────────────────────────────────────────────────────┤ │ │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ │ │ 小范围 │────▶│ 证明可靠 │────▶│ 扩大授权 │───┐ │ │ │ 低风险 │ │ 建立信任 │ │ 做更多 │ │ │ │ │ 可逆操作 │ │ │ │ │ │ │ │ └──────────┘ └──────────┘ └──────────┘ │ │ │ ↑ │ │ │ └─────────────────────────────────────────────┘ │ │ │ │ 反方向（信任崩塌）： │ │ 一次严重失误 → 用户关闭全部权限 → 产品沦为花瓶 │ │ │ │ ⚡ 设计核心：让飞轮正向转动，同时防止一次失误摧毁全盘 │ └─────────────────────────────────────────────────────────┘

围绕这个飞轮，Agent 产品有五个核心设计维度：

维度一：权限分级——"能做什么"的边界设计

问题：Agent 有了工具就等于有了"手脚"，但不是所有手脚都该放开

Day 18 讲了 Tool Schema——每个工具就是一个权限。问题是：产品设计者要决定哪些权限对用户可见、哪些默认开启、哪些需要显式授权。

风险等级操作类型产品设计策略渠道管理对照
🟢 低查询/读取（查数据、看报表）默认开启，无需确认查绩效看报告——随时可看
🟡 中内部变更（写备忘录、建草稿）自动执行，事后通知渠道经理内部记录——做完告知
🟠 中高外部通讯（发邮件、发消息）预览确认后发送给代理商发通知——主管过目后发
🔴 高资金/合同/终止操作必须人工审批+二次确认终止合作/调返利——总监签字
⛔ 禁止删除数据/发布公告/批量操作产品层面直接禁止，不给工具集体辞退——不可能授权任何个人
Agent 设计原则 #1

权限要"从下往上开放"——先让 Agent 只做低风险的事，证明可靠后再逐步解锁更高权限。
反面案例：一上来就让 Agent 可以"自动发送客户通知"——第一天就发错一封，用户永远不敢再用。
正面案例：前两周只让 Agent 起草通知（你审一遍再发）→ 发现准确率 99% → 第三周开放"低风险通知自动发送"。

类比：新员工的权限阶梯

你招了一个新的渠道运营，不管他简历多优秀，第一天绝不会让他自己拍板终止代理商合作。你会设计一条权限升级路径：先跟你一起做 → 独立做低风险的 → 证明判断力后扩大范围 → 最终可以独立处理大部分事务但重大决策仍需汇报。

Agent 产品需要同样的"成长路径"设计。

维度二：预确认设计——"动手前先说"

问题：用户不知道 Agent 要做什么就做了，出事后才发现

好的 Agent 产品在执行动作前，会用清晰的方式告诉用户"我打算做什么"：

┌──────────────────────────────────────────┐ │ 预确认设计的三种模式 │ ├──────────────────────────────────────────┤ │ │ │ 模式 A：Silent Execution（静默执行） │ │ 适用：🟢 低风险操作 │ │ "已为你查询了 Q1 华东区数据" │ │ → 用户看到结果，不需要事先同意 │ │ │ │ 模式 B：Plan → Confirm → Execute │ │ 适用：🟡🟠 中/中高风险操作 │ │ "我计划做以下 3 件事： │ │ 1. 生成绩效异常报告 │ │ 2. 标记 5 个待关注代理商 │ │ 3. 起草预警邮件（待你确认后发送） │ │ 确认执行？" │ │ → 用户看到计划全貌后一键确认 │ │ │ │ 模式 C：Step-by-Step Approval │ │ 适用：🔴 高风险操作 │ │ 每一步都暂停，等用户确认后才继续 │ │ "Step 1 完成。下一步是调整返利比例 │ │ 从 8% → 5%，确认？" │ │ → 最安全但最慢 │ │ │ └──────────────────────────────────────────┘
Agent 设计原则 #2

动作的"可逆程度"决定预确认的"严格程度"。
可逆操作（生成草稿）→ 先做再说（用户可以撤销）
部分可逆（发内部消息）→ 先展示计划再执行
不可逆操作（发外部邮件/修改合同/转账）→ 必须逐步确认

好的 Agent 产品不会让你选这三种模式——它根据操作风险自动选择正确的确认模式。用户不需要理解底层逻辑，产品替他管好了。

维度三：可观测性——"让用户看见 Agent 在想什么"

问题：Agent 是"黑箱"——用户不知道它为什么做了这个决定

Day 16 讲过 CoT——让模型展示推理过程。在 Agent 产品中，可观测性不是技术选项，是产品必需：

  • 决策透明：为什么选了这个动作？（"我选择发邮件给李总因为他连续 2 月低于目标且未回复上次约谈"）
  • 数据溯源：这个判断基于什么数据？（"数据来源：CRM 系统 Q1 数据 + 上月绩效报告"）
  • 置信度标注：Agent 对自己的判断有多确定？（"85% 确信度——有一条数据缺失可能影响判断"）
  • 执行日志：做了什么？什么时候做的？结果是什么？（可审计、可回溯）
Agent 设计原则 #3

"展示推理过程"不是炫技，是建立信任的最低成本方式。
用户信任 Agent 有两种路径：①用了很多次没出过错（耗时长、不确定）；②每次都能看到它的"思考过程"，确认逻辑靠谱后放心让它做（快速建立信任）。
好的 Agent 产品两条路径同时走——显示推理过程+积累正确率数据。

类比：渠道管理中的"下属工作汇报"

你管一个渠道经理，他说"我决定暂停跟代理商张总的合作"。你需要什么？

  • 不是一句结论——你需要为什么（数据依据+推理链条）
  • 不是事后汇报——你需要事前汇报（让你有机会阻止）
  • 不是口头承诺——你需要可追溯的记录（万一出事，能复盘决策过程）

Agent 产品的可观测性设计，就是给 AI 建立一套"工作汇报制度"。

维度四：错误恢复——"出了事怎么办"

问题：Agent 一定会犯错，关键是犯错后的损害能否控制

Day 17 讲过 0.95^10 ≈ 60%——即使每一步 95% 正确，10 步之后整体正确率只有 60%。Agent 产品不能假设不犯错，必须为犯错设计恢复机制。

恢复策略机制适用场景
一键撤销所有操作记录完整的执行日志+逆操作能力内部系统操作（标记/备注/分类）
暂存草稿区外发内容先进"发件箱"等待一个时间窗口邮件/消息类操作（30分钟内可撤回）
影响范围限制单次操作不超过 N 个对象（如最多同时调整 5 个代理商）批量操作场景
自动熔断检测到异常模式立即停止（如"一次性降低 10+ 代理商返利"）所有自动化执行场景
人工回滚窗口重大操作执行后保留 24h 确认期，期间可一键回滚合同/资金/权限类操作
Agent 设计原则 #4

好的 Agent 产品不是"不犯错"，而是"犯错后能快速恢复到安全状态"。
设计目标不是 100% 正确率（不可能），而是：①错误可发现（可观测性）；②发现后可恢复（回滚能力）；③恢复前损害有限（影响范围限制）。
这就是 Day 17 讲的"可靠性三要素"的产品化落地——从抽象原则变成了具体机制。

维度五：渐进授权——"Agent 的成长路径"

问题：用户不可能第一天就完全信任 Agent

最关键的产品设计：Agent 的权限不是静态的，而是根据表现动态调整的。

┌──────────────────────────────────────────────────┐ │ Agent 渐进授权路径 │ ├──────────────────────────────────────────────────┤ │ │ │ Level 0: 只读旁观 │ │ "我发现华东区 3 个代理商数据异常，建议关注" │ │ → Agent 只提供分析，不执行任何动作 │ │ │ │ Level 1: 建议+起草 │ │ "已为你起草预警邮件（附件），确认后我来发送" │ │ → Agent 准备好所有东西，人一键确认 │ │ │ │ Level 2: 自动执行+事后报告 │ │ "已自动发送 3 封预警邮件（详见日志）， │ │ 其中 1 封因代理商信息缺失暂停待确认" │ │ → 大部分自动，异常停下来问 │ │ │ │ Level 3: 完全自治+异常熔断 │ │ Agent 独立运行，仅在异常时通知人 │ │ → 高度信任+异常情况自动刹车 │ │ │ │ ⚡ 升级条件：连续 N 次无误 + 用户主动解锁 │ │ ⚡ 降级条件：一次严重失误 → 自动退回上一级 │ └──────────────────────────────────────────────────┘
Agent 设计原则 #5

Agent 产品必须设计"升降级机制"——根据累计表现自动调整权限，而不是一刀切"全自动"或"全手动"。
升级要缓慢（积累信任），降级要迅速（一次失误立刻降）。这和管理团队一模一样——信任需要长期积累，但可以一次丧失。

类比：渠道经理的"放权路径"

你带一个新渠道经理：

  • 第 1 个月：你做决定，他观察学习（Level 0）
  • 第 2-3 个月：他提方案，你审批后他执行（Level 1）
  • 第 4-6 个月：日常事务他独立处理，每周汇报；异常情况立刻上报（Level 2）
  • 第 7 个月起：完全独立负责，你只看月报和异常告警（Level 3）
  • 如果他某次搞砸了一个大客户：立刻退回 Level 1（重大事项需审批），直到重新证明判断力

同样的管理智慧，直接迁移到 Agent 产品设计。

真实产品对比：Agent 产品设计水平三档

维度初级（Demo级）中级（可用级）高级（可信赖级）
权限分级全部权限一次给分高/低两级五级分层+动态调整
预确认不确认直接做重要操作前确认根据风险自动选模式
可观测性只有结果有执行日志推理链+数据溯源+置信度
错误恢复没有回滚操作可撤销熔断+范围限制+回滚窗口
渐进授权要么全自动要么手动可配置自动化程度根据表现自动升降级
用户感受"很酷但不敢真用""可以用但要盯着""放心交给它，出事它会刹车"
关键洞察

市面上绝大部分 Agent 产品还停留在"初级"——Demo 很震撼，但没有人敢在真实业务中全自动运行。从"初级"到"高级"的差距，不是模型能力的差距，而是产品设计的差距。

这就是为什么 Day 27 讲的"工作流设计能力比模型选择更重要"在 Agent 场景里更加成立——Agent 的底层模型只决定"天花板"，但产品设计决定"用户实际能获得多少价值"。

与 Day 29/30 的设计原则对照

三种 AI 产品的设计核心差异：

对比维度长文本产品(Day 29)多模态产品(Day 30)Agent产品(Day 31)
核心挑战注意力管理模态翻译损耗行动可靠性
错误后果分析偏差（可修正）识别错误（可发现）不可逆动作（已执行）

三层叠加的完整认知

一个成熟的 AI 产品往往同时包含这三层——以你的渠道绩效 Agent 为例：
• Worker A/B 做数据拉取和异常标记 → 长文本设计（怎么从海量数据中聚焦异常）
• Worker E（Day 30 新增）做门店照片分析 → 多模态设计（怎么减少图片识别损耗）
• Orchestrator 做任务分发+Worker C/D 生成报告并通知代理商 → Agent 设计（怎么确保通知不发错）

三层设计原则不是互斥的，而是叠加的。越靠近"行动端"，设计要求越高。

So What — 这改变了你的什么判断

1. 评估 Agent 产品的五问清单

当你评估一个 Agent 产品（自动化工作流/AI助手/智能运营工具）时：

  1. 权限分级：它能做的事有几级？高风险操作有没有单独管控？还是"一个开关全开"？
  2. 预确认机制：它执行动作前会告诉你吗？还是直接做了你才知道？
  3. 推理可见：你能看到它为什么做这个决定吗？有数据来源和置信度吗？
  4. 错误恢复：做错了能撤回吗？有熔断机制吗？还是"覆水难收"？
  5. 渐进授权：能从"半自动"逐步升级到"全自动"吗？还是要么全开要么全关？

5 项齐全 = 生产环境可用；3 项以下 = 只适合内部试验；0 项 = 这不是产品，是个 Demo。

2. Day 21 Agent 系统的产品化升级

如果你真要落地渠道绩效 Agent，Day 21 的架构需要叠加今天的产品设计层：

Day 21 架构+ Day 31 产品设计
Worker A 数据拉取🟢自动执行（只读操作，无风险）
Worker B 异常标记🟡自动执行+事后报告（"标记了5个异常，详见附件"）
Worker C 归因分析🟡Plan-Confirm模式（"我的分析如下...确认这个方向对吗？"）+ 置信度标注
Worker D 对策建议🟠预览确认（"建议给以下3个代理商发预警通知，预览？"）
Orchestrator 全局协调🔴 自动熔断（"检测到Worker C输出不一致，暂停等待人工确认"）+ 执行日志

加上渐进授权路径：第一个月全部 Plan-Confirm → 第二个月 Worker A/B 升级到自动执行 → 第三个月 Worker C 升级到自动+异常停 → Worker D 的通知发送始终保持预览确认（外部操作不可逆）。

3. 与 Day 20 可验证性的闭环

Day 20 讲了"什么任务适合 AI"——可验证性高的任务。今天给这个判断加一个维度：

判断框架更新

Agent 产品适合自动化的任务 = 可验证性高 + 错误后果可控 + 可回滚。
三个条件缺一不可：
• 可验证 + 后果严重 + 不可回滚 → 预确认模式（如转账）
• 可验证 + 后果轻微 + 可回滚 → 全自动（如标记异常）
• 不可验证 + 任何后果 → 人做决定，Agent 只建议

"能不能自动化"不只取决于 AI 准不准，还取决于"准得不够的时候后果多严重"。

4. "Agent 产品成熟度"的行业判断

从今天的框架看当前行业：

  • Manus / Devin 类：技术演示震撼（Level 3 演示），但产品设计还在初级——缺乏精细的权限分级和错误恢复。适合"探索性任务"不适合"生产环境"
  • Claude MCP + Computer Use：权限分级意识强（每个工具显式授权），可观测性好（推理过程可见），但渐进授权机制缺失。企业级 Agent 的"基础设施"方向
  • 垂直 Agent（如 Harvey/法律、Abridge/医疗）：产品设计往往最成熟——因为垂直场景的错误后果清晰可量化，倒逼了完整的恢复和确认机制设计。与多模态场景类似，Agent 场景也是"垂直优于通用"
🎯 Checkpoint
场景：你们团队的"渠道绩效 Agent"已经开发完成 MVP，准备开始内部试用。产品经理问你："第一周就让 Agent 全流程自动运行吗？还是怎么上线？"

目前的 Agent 可以做的事：
① 自动拉取代理商数据 → ② 标记绩效异常 → ③ 生成归因分析报告 → ④ 起草预警邮件 → ⑤ 发送邮件给代理商

内测测试结果：步骤 ①② 准确率 99%+，步骤 ③ 准确率约 88%，步骤 ④ 合格率约 82%，步骤 ⑤ 是自动发送（一旦发就收不回来）。

你建议什么上线策略？
  • A. 全流程自动化上线——88% 和 82% 已经够用了，人工做这事准确率也差不多，AI 的优势是快。让它跑一周看看再说
  • B. 保守起见，Agent 只做到步骤 ②（标记异常），后面全部人工。等准确率到 95% 再逐步放开
  • C. 分层策略：①② 全自动 → ③ 自动生成但人审 → ④ 起草后预览确认 → ⑤ 永远不自动发（外部通讯必须人确认）。两周后根据 ③ 的准确率数据决定是否升级到自动
  • D. 先问三个问题：错误的代价是什么（发错一封邮件的最坏情况）？第 ③ 步 88% 的错误集中在什么类型？能否用规则把"高置信"的自动处理、"低置信"的交给人？
追问 1：假设步骤 ③ 的 12% 错误中，8% 是"方向对但措辞不精确"（影响不大），4% 是"归因方向完全错误"（可能导致错误决策）。这个信息如何改变你的上线策略？

追问 2：产品经理说"如果 Agent 太保守（总是要人确认），渠道经理不愿意用——比手动做还麻烦。"你怎么在"安全"和"效率"之间找到平衡点？用户从什么时刻开始觉得 Agent"有用"？
📌 知识卡片
  • 1. Agent产品的核心命题：不是"让AI做更多"，而是"让AI犯错时伤害最小化"——设计核心从"信息管理"变为"行动可靠性管理"
  • 2. 信任飞轮：小范围低风险可逆操作→证明可靠→扩大授权→做更多 | 一次严重失误→信任崩塌→退回起点。飞轮正向需要长期积累，崩塌只需一次
  • 3. 五条设计原则：权限从下往上开放 / 动作可逆程度决定确认严格度 / 展示推理过程建立信任 / 为犯错设计恢复机制而非假设不犯错 / 根据表现动态升降级
  • 4. 三种AI产品的设计核心差异：长文本=注意力管理 / 多模态=翻译损耗管理 / Agent=行动可靠性管理。三层叠加，越靠近行动端设计要求越高
  • 5. Agent自动化条件三问：可验证吗？+ 错误后果可控吗？+ 可回滚吗？三项全满足才适合全自动；缺一项就需要人介入点
