AI产品设计原则(1)：长文本产品设计

从"能处理长文本"到"长文本产品用起来好"之间，差着一整个产品设计学科
📅 2026-05-18 Mon ⏱️ 约 40 分钟 🟡 中半衰期
🔥 开场问题

Kimi 号称支持 200K Token 上下文窗口——你把一份 80 页的代理商合同扔进去说"帮我审核"，它确实会给你一份看起来像样的审核报告。但如果你换一种方式——先问它"这份合同有几方主体"，再逐步追问"甲方核心义务有哪些"——你会发现，同一个模型、同一份文件，两种用法的输出质量可能差两倍。

这说明什么？"模型能力"和"产品体验"之间，存在一个巨大的设计空间。长文本的技术壁垒正在消融（Day 25 已讲过），那竞争到底在什么层面？今天我们从"技术选型者"的视角转向"产品设计者"的视角——不再问"该用哪个模型"，而是问"怎么设计一个好的长文本产品"。

10 min

Why — 为什么要单独讲"长文本产品设计"

1. 技术能力 ≠ 产品价值

Day 10 我们讲了 Context Window 的成本经济学，Day 25 讲了 Kimi 的长文本战略押注。结论很清楚：长上下文已经不再是稀缺能力——GPT-4o 128K、Claude 200K、Gemini 2M、Kimi 200K，窗口越来越大。

但现实是：大部分用户依然不知道怎么"用好"长文本。典型场景——

  • 把一整本 PDF 丢进去问一个笼统问题 → 得到一个泛泛的摘要
  • 把 10 份文件一起上传 → 模型幻觉暴涨，引用张冠李戴
  • 对话到第 8 轮 → 之前的信息被"遗忘"（不是真遗忘，是注意力分配的 Lost in the Middle 效应——Day 10）

这些不是模型 bug，是产品没有为用户管理好"信息→注意力→输出"这条链路。

类比：渠道管理

你手里有 200 个代理商的全量经营数据——数据量不是问题。但如果你直接把 200 张报表摆在桌上说"帮我分析"，新来的数据分析师多半给你一个无用的全面总结。而如果你说"先看华东区环比下降超 15% 的 5 家"，质量立刻不一样。

信息的"投喂方式"决定了分析质量。这对 AI 同样成立。

2. 产品设计是新的壁垒

Day 27 的核心结论之一：模型能力正在趋同，差异化正从模型层转向产品层。当每家都有 200K+ 窗口时——

  • 差异不在"能不能吃下 200K"（这只是准入门槛）
  • 差异在"用户扔进 200K 内容后，产品怎么引导用户提出好问题，怎么帮模型分配注意力，怎么呈现高信息密度的输出"

这就是为什么"AI 产品设计"将成为接下来 3-5 年的核心竞争力——不是技术壁垒，是体验壁垒。

核心认知转变

Day 22-28 我们一直在问"选哪个模型"——这是供给侧视角。
Day 29 开始，我们转向问"怎么把模型变成好用的产品"——这是需求侧+设计侧视角。
从模型选型者 → 产品设计者，这是第三模块后半程的核心跃迁。

20 min

What — 长文本产品设计的本质框架

核心命题：信息管理三角

长文本产品的设计本质是管理一个三角关系：

┌─────────────────────────────────────────────────────┐ │ 长文本产品设计 · 信息管理三角 │ ├─────────────────────────────────────────────────────┤ │ │ │ ┌──────────┐ │ │ │ 用户意图 │ ← 产品要帮用户表达清楚 │ │ └─────┬────┘ │ │ │ │ │ ┌────────┼────────┐ │ │ ▼ ▼ │ │ ┌──────────┐ ┌──────────┐ │ │ │ 信息定位 │ │ 输出呈现 │ │ │ │（找到相关 │ │（信息密度 │ │ │ │ 段落） │ │ ×可理解 │ │ │ │ │ │ 性） │ │ │ └──────────┘ └──────────┘ │ │ ↑ ↑ │ │ │ ┌──────────┐ │ │ │ └───│ 注意力 │──┘ ← 产品要帮模型分配注意力 │ │ │ 分配策略 │ │ │ └──────────┘ │ └─────────────────────────────────────────────────────┘

三角的三个顶点，就是长文本产品需要解决的三个核心设计问题：

  1. 用户意图管理：帮用户把模糊的需求变成精准的指令
  2. 信息定位策略：帮模型在海量文本中找到真正相关的内容
  3. 输出呈现设计：把模型的分析结果以高信息密度+可操作的方式呈现

设计维度一：用户意图管理

问题：用户不知道该怎么"问"

用户面对一份 80 页合同，最自然的操作是"帮我审核一下"。但这个需求太模糊——

  • 审核什么？合规风险？商业条款？付款条件？违约责任？
  • 对谁来说是"好"的审核？法务？业务？管理层？
  • 什么算"审核完了"？逐条确认？标出异常？给出建议？

三种设计模式

模式机制适用场景典型产品
引导式提问产品先提出结构化问题帮用户聚焦新用户/不熟悉文档类型NotebookLM 的自动问题建议
预设意图模板按文档类型提供常见分析模板高频重复场景（合同/研报/论文）Kimi 的"快速摘要/逐章分析/关键信息提取"
渐进式深钻先给概览→用户点击感兴趣的点→展开细节探索性分析/决策支持ChatPDF 的问答+高亮联动
产品设计原则 #1

不要让用户对着空白输入框和长文档发呆。好的长文本产品应该在用户上传文档的瞬间就"主动出击"——告诉用户"我已经读完了，这里有几个你可能关心的方向"。

类比：渠道管理中的"引导式对话"

这跟你带新渠道经理时的策略一模一样：

  • ❌ "帮我看看华东区情况" → 新人：给你写 20 页什么都有的报告
  • ✅ "关注华东区三个问题：哪些代理商环比降了 15% 以上？原因是什么？下月怎么干预？" → 新人：3 页精准聚焦

好的产品 = 好的上司：把模糊需求结构化后再委派。

设计维度二：信息定位策略

问题：200K 窗口里，模型的注意力不是平均分配的

Day 10 讲的 "Lost in the Middle" 效应——模型对文档开头和结尾的信息利用率远高于中间部分（中间部分利用率可能只有 50-60%）。这意味着：

反直觉事实

"把文件全扔进去让模型自己找"——这个最简单的方案，往往不是体验最好的方案。因为信息越多，注意力越分散，中间段落的重要内容越容易被忽略。

四种信息定位策略

策略机制优势劣势
全量注入整份文档塞进上下文无信息损失、实现最简注意力分散、成本高、中间遗漏
RAG 检索向量检索相关段落后注入成本低、聚焦、无中间遗漏检索不准=信息损失、跨段引用丢失
层级摘要先摘要再按需展开原文信息密度高、全局不遗漏摘要有损、细节可能丢失
混合策略摘要全文+RAG 检索重点段+原文确认最佳体验、兼顾全局和细节工程复杂度高、延迟增加

真正高级的做法：分层注意力引导

最好的长文本产品不是简单地"把文档丢给模型"——而是在模型看到文档之前，先帮它建一个"注意力地图"：

  1. 第一层（全局索引）：自动生成文档结构大纲 + 关键实体列表
  2. 第二层（焦点定位）：根据用户意图，确定需要深度阅读的章节
  3. 第三层（精读+引用）：对焦点章节全文注入，其他章节仅保留摘要
产品设计原则 #2

帮模型"划重点"——就像你给下属说"重点看第三章和附件二，其他浏览就行"。这比"你看完这 200 页告诉我想法"效率高一个数量级。

设计维度三：输出呈现设计

问题：长文本的分析结果本身可能也很长

你让 AI 审核一份 80 页合同，它给你写了 15 页分析报告——这反而增加了你的信息处理负担。好的产品需要：

输出设计的三层金字塔

┌──────────────────────────────────┐ │ 第一层：一句话结论 │ ← 30秒了解核心 │ "此合同有 3 处高风险条款" │ ├──────────────────────────────────┤ │ 第二层：结构化摘要 │ ← 3分钟掌握全貌 │ 风险1: 无限连带责任(§7.2) │ │ 风险2: 单方解除权缺失(§12.1) │ │ 风险3: 违约金比例过高(§15.4) │ ├──────────────────────────────────┤ │ 第三层：原文定位+详细分析 │ ← 按需深入 │ 点击任一条 → 跳转原文高亮位置 │ │ + AI 的逐条分析和修改建议 │ └──────────────────────────────────┘

核心设计原则：让用户选择要消费多深的信息，而不是一次性灌满。

产品设计原则 #3

输出应该是"金字塔结构"——结论→摘要→详情。用户默认只看顶层，需要时再一层层展开。就像好的渠道汇报：一句话结论+3个关键数据+详细附录——老板看第一层就够了，想追问再往下看。

设计维度四：多轮对话中的上下文管理

问题：上下文越积越长，前面的信息被"挤出"注意力范围

用户跟 AI 讨论一份长文档，对话本身也在消耗上下文窗口。第 10 轮对话时——

  • 对话历史可能已经占了 30-50K tokens
  • 加上文档本身 100K+ tokens
  • 总共 150K+ → 早期对话中的关键结论可能已被模型"稀释"

三种上下文管理策略

策略做法体验效果
对话摘要压缩每 5 轮自动将前序对话压缩为关键结论保住重要结论，释放窗口空间
文档引用锁定用户标记的重要段落始终保持在上下文前端用户主动选择"不允许遗忘"的内容
分析状态持久化每轮分析结果存为结构化笔记，后续引用笔记而非重新分析不重复工作，结论不丢失
产品设计原则 #4

产品要替用户管理"什么该记住、什么可以忘"。就像好的项目管理：每次会议的关键决策写入决议表，下次开会先回顾决议而非翻聊天记录。

真实案例对比：三个长文本产品的设计差异

维度ChatGPT + 文件上传KimiNotebookLM (Google)
意图管理❌ 无引导，纯空白对话框🟡 提供快捷操作（摘要/提问）✅ 自动生成问题+大纲+音频概述

关键洞察

NotebookLM 在模型能力上可能不如 GPT-4o 或 Claude——但它在产品设计层领先一个代际。它的核心创新不是"模型更强"，而是"重新定义了人和长文本之间的交互方式"。这就是为什么 Google 选择在 Gemini 之外单独做 NotebookLM——它不是模型产品，是设计产品。

长文本产品设计的五条铁律

基于以上分析，总结五条不依赖特定模型版本的设计原则：

  1. 主动出击：文档上传后 3 秒内给用户可操作的"下一步"，不要让人对着空白框想问题
  2. 注意力引导：帮模型划重点——用户意图 × 文档结构 = 聚焦范围
  3. 金字塔输出：结论→摘要→详情三层，默认展示最精简层
  4. 源引用锚定：每一条分析结论都必须可追溯到原文位置（对抗幻觉）
  5. 记忆管理：多轮对话中，关键结论不允许被稀释

So What — 这改变了你的什么判断？

1. 评估 AI 产品的新维度

Day 22-28 你学会了评估模型供应商的框架（五维度/七维度）。今天开始，你需要加一个平行维度：产品设计质量。

评估维度模型层面（Day 22-28）产品层面（Day 29+）
核心问题"这个模型强不强？""这个产品好不好用？"
竞争壁垒来源技术参数、训练数据、算力交互设计、工作流、用户习惯
迭代周期3-6 个月发新版每周可优化细节
护城河持久性容易被追平（能力趋同）更持久（用户习惯难迁移）
职业启示

如果你想在 AI 时代建立个人壁垒——"理解什么是好的 AI 产品设计"比"懂最新模型参数"更值钱。模型参数 6 个月就过时，设计原则 3-5 年有效。回顾 Day 28 的操作系统保质期：设计原则属于"框架"层（2-3 年），模型参数属于"公司结论"层（3-6 个月）。

2. 渠道管理 AI 工具评估的产品设计清单

用今天的框架去评估你手里的渠道数据分析 AI 工具：

  • ✅ 上传月度绩效报表后，是否主动给出"这个月 3 个最值得关注的异常"？
  • ✅ 分析 50 个代理商的数据时，是否有注意力引导（先看异常再看正常）？
  • ✅ 输出是否是"金字塔结构"——一句结论+关键数据+详细分析+原始数据引用？
  • ✅ 多轮追问时，是否记得前几轮已经确认的结论？

四个✅的工具值得深度用；少于 2 个的，要么自己设计 Prompt 弥补，要么换工具。

3. 从"用 AI"到"设计 AI 工作流"的升级

Day 21 的实战课你设计了渠道绩效 Agent 系统。那时候的设计重点是"后端逻辑"——拆任务、选模型、设质量门。

今天补上"前端设计"——如果你的 Agent 系统需要面向渠道经理使用，那你需要在 Day 21 的架构上叠加今天的产品设计原则：

  • 渠道经理上传区域报表后 → 主动出击：自动标出 3 个最大的环比变动
  • 多维度数据交叉分析时 → 注意力引导：按"异常程度"排序，不是按代理商编号排序
  • 输出绩效报告时 → 金字塔结构：一页纸 + 详细附录，不是 15 页平铺
  • 渠道经理追问"为什么这家降了 30%"时 → 记忆管理：记住之前已分析过的全局结论
🎯 Checkpoint
场景：你的团队准备采购一个"AI 合同审核助手"给法务部用。两家供应商 Demo：

供应商 A：用了最新的 Claude 3.5（200K 窗口），上传合同后直接给一份完整审核报告——列出所有潜在风险、每条引用原文条款号。模型能力强，报告很详细（通常 8-12 页）。

供应商 B：用的是 GPT-4o（128K 窗口），但产品做了分层设计——上传后先给"3 个最高风险条款+风险等级+一句话说明"，法务人员点击任一条可展开详细分析和原文高亮，还能标记"已确认/需修改"直接生成修改建议。

你怎么建议老板选？
  • A. 选供应商 A——模型更强（Claude 200K > GPT-4o 128K），合同审核准确率和完整性才是第一位，产品交互可以后续改
  • B. 选供应商 B——产品设计更好，法务人员实际使用效率更高，模型能力差距在这个场景不是决定性的
  • C. 让两家各审核同一批 10 份合同，对比遗漏率和误报率——数据说话
  • D. 先问法务部"你们现在审核一份合同的痛点到底是什么——是漏看风险，还是效率太低？"——痛点不同，选型标准不同
追问 1：如果法务说"两个都是痛点——既怕漏风险又嫌慢"，那 A 和 B 的取舍逻辑是什么？给出你的判断。

追问 2："产品交互可以后续改"这个说法成立吗？为什么很多 AI 产品的交互设计事后很难改？
