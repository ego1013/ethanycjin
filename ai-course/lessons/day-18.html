Day 18 · Agent 的工具调用与记忆机制

AI 怎么「记住」你？

📅 2026-04-30 Thu 📦 第二模块 · 应用篇 · Week 4 ⏱️ 预计 40 分钟
🔥 开场

你今天正在使用的这套课程系统——Coach M——它是怎么做到"记得你上节课学了什么""知道你偏好选择题""还能每天上午 10:30 准时推送"的？

答案是：它不是一个"更聪明的 ChatGPT"，它是一个 Agent。

每天早上它醒来时，第一件事是读取记忆文件——读你的学习档案、读上一课的内容、读反馈日志。然后它调用工具——写 HTML 文件、更新大纲、执行部署脚本。最后它把课程推送给你。

昨天我们讲了 Agent 的"是什么"——四个组件（大脑+手脚+记忆+规划）。今天我们要打开其中两个组件的黑箱：

工具调用到底是怎么实现的？ 模型一个只会预测下一个 Token 的概率机器（Day 1 的心智模型），它是怎么"调用数据库"的？

记忆到底是怎么存的？ Context Window 有上限（Day 10），对话结束后上下文就消失了——那 Agent 怎么做到"认识你"？

10 min

Why — 为什么「怎么调用工具」和「怎么记忆」是 Agent 的两个关键瓶颈？

从 Day 17 的四组件回顾说起

昨天我们说 Agent = 大脑 + 手脚 + 记忆 + 规划。你可以把这四个组件的"成熟度"做一个排序：

组件 当前成熟度 原因
大脑（LLM 推理） ★★★★☆ GPT-4/Claude/o1 推理能力已经很强
规划（任务拆解） ★★★☆☆ CoT + 推理模型让规划更可靠，但复杂任务仍不稳定
手脚（工具调用） ★★★☆☆ Function Calling 已标准化，但工具选择和参数填充仍有出错率
记忆（持久化信息） ★★☆☆☆ 最不成熟的环节——跨对话记忆没有统一方案，各家都在摸索

看到了吗？记忆是 Agent 四大组件中最不成熟的。工具调用已经有了 Function Calling 这个标准协议（等于"大家都学会用手了"），但记忆——怎么让 AI 跨对话持续认识你——至今没有一个公认的最优解。

💡 为什么这两件事值得深讲

工具调用决定了 Agent 能做什么——能调用什么工具，就有多大的行动范围。理解 Function Calling 的工作原理，你才能判断"这个 Agent 产品的能力边界在哪里"。

记忆决定了 Agent 能做多好——没有记忆的 Agent 每次都是陌生人，你得重复交代所有背景。有记忆的 Agent 越用越懂你，就像一个跟了你三年的助理。

合在一起：工具让 Agent 有用，记忆让 Agent 好用。

一个来自渠道管理的直觉类比

想象你新招了一个渠道运营助理。两件事决定了他能不能真正上手：

第一，你给他开了哪些系统权限？（= 工具调用）
只给 CRM 只读权限，他只能看数据；给了 CRM 写权限 + 邮箱权限 + 报表系统权限，他才能真正帮你干活。权限清单就是"工具列表"，他需要知道自己有哪些权限、每个权限怎么用。

第二，他了不了解你的工作上下文？（= 记忆）
如果他每天来上班都不记得前一天的对话——不知道华东区哪个代理商在整改、不记得你上次让他追踪的指标——他每天都是"新员工第一天"。你得反复交代背景，效率极低。

权限 × 上下文 = 真正能干活的助理。 今天我们就来看看 Agent 是怎么解决这两件事的。

20 min

What — 本质是什么？

Part A · Function Calling：让 LLM "长出手脚" 的标准协议

最关键的一个认知：模型并不"执行"工具

这是初学者最常混淆的一点：大模型自己不会执行任何操作。它不会发邮件，不会查数据库，不会调 API。它唯一会做的事情——从 Day 1 你就知道了——是预测下一个 Token。

那"工具调用"到底怎么发生的？答案异常简单：

📖 Function Calling 的本质

模型不执行工具。它只是生成一段特殊格式的文本——一段"我想调用 X 工具，参数是 Y"的结构化输出。

真正执行工具的是外部系统——Agent 的"运行时框架"（runtime）收到这段文本后，去调用真正的 API、数据库、邮件服务。

然后把执行结果塞回给模型，让模型继续下一轮推理。

整个过程可以用一张图说清楚：

Function Calling 的完整生命周期

┌─────────────┐
│ 你 (用户) │ "帮我查华东区代理商出货数据"
└──────┬──────┘
       ↓ Prompt + 工具清单
┌─────────────┐
│ LLM (大脑) │ "我需要调用 query_database"
│ │ → 输出：{ "tool": "query_database", "args": {...} }
└──────┬──────┘
       ↓ 结构化 JSON（不是人类文字）
┌─────────────┐
│ 运行时 │ 收到 JSON → 真正调用数据库 API
│ (Runtime) │ → 获取查询结果
└──────┬──────┘
       ↓ 工具执行结果（数据）
┌─────────────┐
│ LLM (大脑) │ 拿到数据 → 分析 → 决定下一步
│ │ → 或继续调用工具，或输出最终回答
└─────────────┘

关键洞察：模型只是在 NTP 的过程中，"碰巧"预测出了一段结构化文本（JSON格式的工具调用指令）。它之所以能做到这一点，是因为训练数据中包含了大量"在什么场景下应该调用什么工具"的示例。

工具清单（Tool Schema）：Agent 的"权限列表"

在每次对话开始时，系统会把可用工具的描述塞进 Prompt（系统提示词）里。这就是告诉模型"你有哪些权限"： 

// 工具清单示例（简化版）
tools: [
  {
    "name": "query_database",
    "description": "查询公司内部数据库，获取代理商绩效数据",
    "parameters": {
      "region": "地区筛选（如：华东/华南/华北）",
      "metric": "指标类型（如：出货量/回款/新签）",
      "period": "时间范围（如：2026-Q1）"
    }
  },
  {
    "name": "send_email",
    "description": "发送邮件给指定收件人",
    "parameters": {
      "to": "收件人邮箱",
      "subject": "邮件主题",
      "body": "邮件正文",
      "attachment": "附件路径（可选）"
    }
  },
  {
    "name": "create_report",
    "description": "生成 Excel 报表文件",
    "parameters": { ... }
  }
]

模型看到这个列表后，就"知道"自己有三个工具可用、每个工具需要什么参数。它在推理过程中，会基于用户的需求和当前状态来决定调用哪个工具、填什么参数。

💭 管理者视角

Tool Schema 本质上就是你给下属写的"系统权限说明书"：

• 权限名称（name）= 他能做什么
• 权限描述（description）= 什么时候该用
• 参数说明（parameters）= 具体怎么操作

写得越清晰，他用得越准确——Tool Schema 的质量直接决定工具调用的准确率。这就是 Day 15 CRISP 的延伸——你不只要给模型写好 Prompt（派活），还要给它写好 Tool Schema（操作手册）。

MCP：工具调用的"USB 标准"

2024 年底，Anthropic 提出了 MCP（Model Context Protocol）——一个标准化的工具接口协议。这是什么意思？

类比：USB 出现之前，每个设备用自己的接口——打印机一根线、键盘一根线、手机一根线，互不兼容。USB 出现后，所有设备用同一个口——即插即用。

MCP 做的是同一件事：让任何工具都能用统一的协议接入任何 Agent。不管你的 Agent 用的是 GPT-4 还是 Claude 还是 Kimi，不管你的工具是数据库还是邮箱还是 CRM——只要都遵守 MCP 协议，就能互联互通。

维度 MCP 之前 MCP 之后
工具接入 每个 Agent 平台定义自己的工具接口格式 统一协议，一次开发到处使用
生态效应 工具开发者需要适配多个平台 适配一次即可，生态爆发
类比 各种专有接口（PS/2、串口、并口） USB / USB-C 统一标准

MCP 目前还在早期采用阶段，但方向是确定的：工具调用正在从"各家私有协议"走向"行业标准化"。这意味着未来的 Agent 能接入的工具数量会指数增长——就像 USB 设备的爆发一样。

Function Calling 的失败模式

工具调用不是 100% 可靠的。三种常见失败：

失败类型 表现 根因 类比
选错工具 该查数据库却去搜网页 Tool Schema 描述不清或场景判断错误 下属不知道该找谁办事
参数填错 查询条件写错、时间范围错误 参数说明不够明确或模型理解偏差 下属填错了审批单
该调不调 该查数据时直接编造答案 模型"自信过头"，觉得自己知道答案 下属凭感觉报数而不查系统
⚠️ 关键警示

第三种失败——"该调不调"——本质上就是 Day 6 讲的幻觉在 Agent 场景下的升级版。Chatbot 编造答案只是给你一段错误文字；Agent 编造答案意味着它跳过了关键验证步骤直接行动——比如跳过数据查询直接编造分析报告。

这就是为什么 Tool Schema 的 description 字段极其重要——你要在描述里明确告诉模型"当需要 X 信息时必须调用此工具，禁止凭推测回答"。

Part B · 记忆机制：让 Agent "认识你" 的三种方式

问题的起点：为什么记忆这么难？

回到 Day 10 的核心认知：Context Window 是有上限的，而且很贵。

一次对话结束，上下文消失——模型回到"白板状态"。它不"知道"你是 Ethan，不"知道"你是做渠道管理的，不"知道"你上次让它分析了什么。

这就产生了一个工程问题：怎么在 Context Window 的物理约束下，让 Agent 拥有"持续记忆"的效果？

答案是三种技术方案，各有利弊——

方案 1：上下文注入（Context Injection）

最简单也最直接的方式：每次对话开始前，把相关的记忆信息直接塞进 System Prompt。

上下文注入的工作方式

┌─────────────────────────────┐
│ 记忆存储（文件/数据库） │
│ • 用户档案：Ethan, 渠道管理 │
│ • 偏好：选择题 Checkpoint │
│ • 上次进度：Day 17 已完成 │
└───────────────┬─────────────┘
                ↓ 对话开始时读取
┌─────────────────────────────┐
│ System Prompt │
│ "你是 Coach M，学习者是 Ethan..." │
│ "上次学到 Day 17，主题是 Agent..." │
│ "Ethan 偏好选择题+量化追问..." │
└───────────────┬─────────────┘
                ↓ 塞入每次 LLM 调用
┌─────────────────────────────┐
│ LLM 看到的 = 记忆 + 当前对话 │
│ → 模型"以为"自己一直记得你 │
└─────────────────────────────┘

你正在体验的 Coach M 课程系统就是用这种方式。 每天上课前，它读取 SYLLABUS.md、LEARNER_PROFILE.md、FEEDBACK_LOG.md，把关键信息塞进 System Prompt——然后它就"记得"你了。

优点 缺点
✅ 实现简单——读文件/读数据库，塞进 Prompt ❌ 受 Context Window 大小限制——记忆太多塞不下
✅ 信息精确——你精心维护的记忆文件质量高 ❌ 需要人工维护记忆文件（或用代码自动维护）
✅ 可解释——你知道 Agent 记住了什么 ❌ 随着记忆增长，信息选择变成新问题
✅ 最佳适用场景

记忆量中等（几千字以内）、信息更新频率可控、对精确度要求高。
典型例子：个人 AI 助手的用户画像、项目 Agent 的上下文配置、今天你正在用的课程系统。

方案 2：向量检索记忆（RAG-based Memory）

当记忆量超出 Context Window 能承载的范围时，怎么办？Day 12 讲过的 RAG 技术派上用场了——把记忆存成向量数据库，按需检索。

RAG-based Memory 的工作方式

┌─────────────────────────────┐
│ 记忆存储（向量数据库） │
│ • 数百条历史对话摘要 │
│ • 过去 6 个月的工作决策记录 │
│ • 用户所有的偏好和习惯 │
└───────────────┬─────────────┘
                ↓ 当前对话触发"相关记忆检索"
┌─────────────────────────────┐
│ 检索引擎 │
│ 用户问"华东区代理商" → │
│ 检索到 5 条相关记忆 │
│ (上次分析结果/代理商 C 整改中/...) │
└───────────────┬─────────────┘
                ↓ 只注入相关记忆（不是全部）
┌─────────────────────────────┐
│ LLM 看到的 = 相关记忆 + 当前对话 │
│ → 按需召回，不浪费上下文空间 │
└─────────────────────────────┘

核心逻辑：不是把所有记忆都塞进去，而是根据当前对话内容检索最相关的记忆片段。这样即使记忆量巨大，每次实际消耗的 Context Window 空间也是可控的。

优点 缺点
✅ 可扩展——记忆量不受 Context Window 限制 ❌ 检索质量是瓶颈——可能召回不相关的或遗漏关键的
✅ 自动化——无需人工维护，对话结束自动存入 ❌ "记忆衰减"——老旧记忆可能永远不被召回
✅ 适合长期使用——用得越久记忆越丰富 ❌ 难以解释——你不知道它具体"记住了"什么
✅ 最佳适用场景

记忆量大（数万到数十万字）、需要长期积累、对"精确召回每一条"的要求不极端高。
典型例子：ChatGPT 的 Memory 功能、企业级客服 Agent 的客户历史记录。

方案 3：结构化摘要记忆（Summarization Memory）

第三种方案是一个混合策略：每次对话结束后，Agent 自动生成一份对话摘要，存入结构化存储。下次对话时，把摘要注入上下文。

Summarization Memory 的工作方式

┌─────────────────────────────┐
│ 对话结束时 │
│ LLM 回顾整次对话 → │
│ 生成结构化摘要： │
│ • 关键决策：选了方案 C │
│ • 新增信息：代理商 E 下月到期 │
│ • 用户偏好：喜欢先看数据再看结论 │
└───────────────┬─────────────┘
                ↓ 存入记忆库
┌─────────────────────────────┐
│ 记忆库 │
│ 按时间/主题/重要度分层存储 │
│ 定期合并压缩（旧的摘要 → 更简短） │
└───────────────┬─────────────┘
                ↓ 下次对话时注入
┌─────────────────────────────┐
│ LLM 看到的 = 历史摘要 + 当前对话 │
└─────────────────────────────┘
优点 缺点
✅ 信息密度高——摘要比原始对话紧凑得多 ❌ 摘要过程会丢失细节——模型决定什么"值得记住"
✅ 可控——可以设置摘要规则和结构 ❌ 需要额外的 LLM 调用（生成摘要本身有成本）
✅ 随时间自然压缩——越老的记忆越精简 ❌ 摘要质量取决于模型能力——可能遗漏关键信息
✅ 最佳适用场景

对话频繁但每次核心信息有限、需要长时间跨度的记忆但不需要逐字回忆。
典型例子：个人 AI 日记助手、心理咨询 Agent 的会谈记录、项目管理 Agent 的会议纪要。

三种方案的对照总结

维度 上下文注入 向量检索 结构化摘要
容量 受限（几千字） 无限 中等（持续压缩）
精确度 最高（你精心维护） 取决于检索质量 中等（摘要有损）
维护成本 高（需要人工/代码维护） 低（自动存入） 中（需要设计摘要规则）
可解释性 最强（你知道它记了什么） 弱（黑箱检索） 中（摘要可审阅）
适用阶段 MVP / 少量用户 大规模 / 长期 中间态 / 混合使用
💡 实际中的最优解：三者混合

现实中最好的 Agent 记忆系统通常同时使用三种方案：

• 核心身份信息（你是谁、你做什么工作、你的偏好）→ 上下文注入（永久在 System Prompt 里）
• 大量历史交互（过去 100 次对话的细节）→ 向量检索（按需召回）
• 中期工作上下文（最近一周的进展和决策）→ 结构化摘要（定期压缩）

这就像人的记忆系统：核心身份是"自我意识"（永远在），长期经历是"长期记忆"（需要触发才想起），最近发生的事是"工作记忆"（随时可用但会衰减）。

记忆机制的失败模式

和工具调用一样，记忆也有失败模式：

失败类型 表现 后果
遗忘 该记住的没记住 "你上次不是说过了吗？" → 用户沮丧
幻忆 "记住"了不存在的事情 基于错误记忆做出错误判断
过时 记住了已过期的信息 用旧数据/旧决策指导当前行动
泄露 跨用户/跨会话记忆串扰 隐私风险——记忆了不该记的

"幻忆"特别值得注意——它是 Day 6 幻觉 + 记忆 的叠加产物。模型可能"记住"一条它编造的信息，然后在后续对话中把这条幻觉当作事实反复引用。错误记忆比没有记忆更危险——因为它带着"我记得上次就是这样"的权威感。

8 min

So What — 这改变了什么？

一、评估 Agent 产品的新框架

从今天开始，当你评估任何 Agent 产品时，你可以问两个精确的问题：

📖 Agent 产品评估双问法

Q1：它的工具集有多宽？
它能连什么——数据库？邮箱？CRM？文件系统？浏览器？每个工具的参数定义有多精确？工具间能否组合使用？

Q2：它的记忆有多深？
它用什么记忆方案？能记住多久之前的对话？会不会忘记关键信息？你能查看/修改/删除它的记忆吗？

工具集 = 能力半径。记忆 = 理解深度。两者相乘 = 真实可用度。

二、渠道管理中的 Agent 设计思考

假设你要为渠道管理团队设计一个 Agent，用今天学到的知识来规划：

工具调用设计

工具 用途 风险等级 是否需要 Human-in-the-Loop
query_crm 查询代理商数据 🟢 低（只读） 否
generate_report 生成分析报表 🟢 低（只生成不发送） 否
send_notification 发消息给区域经理 🟡 中（对外通讯） 是——发送前让你确认内容
update_status 更新代理商状态标签 🟡 中（修改数据） 是——批量修改前审核列表
adjust_rebate 调整返利金额 🔴 高（涉及资金） 必须——每笔都需要审批

看到了吗？工具的风险等级直接决定了 Human-in-the-Loop 的粒度。低风险的操作（只读查询）可以放手让 Agent 自动执行；高风险的操作（涉及资金）必须每次都经过人工审批。这和你管理团队时"给不同层级的审批权限"是完全一样的逻辑。

✅ Checkpoint · Day 18

场景：你设计了一个渠道管理 Agent，其中一个功能是"每月自动审核代理商返利资格"。审核逻辑涉及 5 个条件（和 Day 16 的场景一样）。现在你需要决定：这个 Agent 的记忆机制怎么设计？

A 不需要记忆——每次审核时把 5 个条件和当月数据都传进去就行。反正每月独立审核，不需要知道历史。
B 纯向量检索——把过去 12 个月所有审核记录存入向量数据库，每次审核时检索相关历史。这样它能"记住"每个代理商的历史轨迹。
C 三层混合：永久层（审核规则+条件定义，上下文注入）+ 中期层（近 3 个月每个代理商的审核结果摘要）+ 长期层（超过 3 个月的记录存向量数据库按需检索）。
D 先问"记忆对审核结果有没有实质性影响"——如果 5 个条件全是当月客观数据（不需要历史对比），那方案 A 就够了；如果有些条件涉及"趋势判断"或"连续 N 个月表现"，才需要加记忆层。先分析哪些条件需要历史信息，再按需设计记忆方案。

⚡ 追问：假设 5 个返利条件中有 2 个涉及"连续 3 个月表现"（需要历史数据），另外 3 个只看当月数据——你会为这 2 个条件选择什么记忆方案？存储的信息量大约是多少（量级估算）？

📌 知识卡片

1 Function Calling 的本质：模型不执行，只生成"调用指令"
LLM 不会查数据库、不会发邮件。它只是在 NTP 过程中生成一段结构化 JSON——"我要调用 X 工具，参数是 Y"。真正执行操作的是外部运行时系统。模型之所以能准确生成工具调用，是因为训练数据中有大量这类示例 + System Prompt 里注入了工具清单（Tool Schema）。
2 Tool Schema = Agent 的"系统权限说明书"
工具清单的 name/description/parameters 三要素直接决定了 Agent 能做什么、什么时候做、怎么做。description 写得越精确，工具调用出错率越低。这和给下属写清楚的 SOP 是同一件事。MCP 协议正在推动工具接口标准化，类似从专有接口到 USB 的升级。
3 Agent 记忆三方案：注入 / 向量检索 / 结构化摘要
上下文注入（精确但容量有限）、向量检索记忆（可扩展但检索质量不稳定）、结构化摘要（信息密度高但有损压缩）。现实中最好的方案是三者混合：核心身份上下文注入 + 大量历史向量检索 + 中期进展结构化摘要。
4 记忆的四种失败：遗忘 / 幻忆 / 过时 / 泄露
遗忘（该记没记）导致用户反复交代；幻忆（记了不存在的事）比没有记忆更危险——错误信息带着"历史依据"的权威感被反复引用；过时（旧信息未更新）导致错误判断；泄露（跨用户串扰）引发隐私风险。设计 Agent 记忆时，"什么时候忘记/更新/删除"和"什么时候记住"同样重要。
5 Agent 产品评估双问法：工具集有多宽 × 记忆有多深
工具集决定 Agent 的能力半径（它能做什么），记忆决定 Agent 的理解深度（它有多懂你）。两者相乘才是"真实可用度"。一个有 100 个工具但不记住你的 Agent，每次都是陌生人；一个记忆完美但没有工具的，还是只能给你建议。
